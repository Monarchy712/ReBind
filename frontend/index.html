Compliance-restricted real-world assets

Identity outlives the key.

A permissioned asset can only move between wallets that passed KYC. So when the holder's key is lost or stolen, the asset is stranded — the compliance gate that stops the thief stops the owner too. Rebind moves it to another wallet the same verified person already controls, on evidence the issuer cannot fabricate.

Evidence
One customerId, two wallets. Read from Cleanverse, signed EIP-712 off-chain.
Gate
ERC-1404 transfer restrictions, enforced by the token itself.
Safety
Freeze on claim, then a challenge window a human can reject inside.

How it works

Three decisions carry the design. Each one is about limiting what a compromised party can do.

01

The evidence lives off-chain

A contract cannot call an HTTP API. But the fact that two wallets belong to one person exists only in Cleanverse's query_apass_list. An attestor reads it and signs an EIP-712 attestation; RecoveryQueue runs ecrecover and trusts the signer — never whoever submitted the transaction.

02

The token enforces its own rules

Transfers pass through ERC-1404: detectTransferRestriction returns a numeric code, messageForTransferRestriction the human reason. An unverified destination is refused by the asset itself, with no coordination from anyone off-chain.

03

Freeze first, review second

Opening a claim freezes the old wallet in the same transaction, so a stolen key cannot race the recovery it triggered. Only then does the challenge window run, giving a reviewer time to reject an impersonation before anything moves.

The issuer can approve a claim, and can reject one. It can never manufacture one — the identity evidence comes from a system the issuer does not control. The property everything else is built to protect
